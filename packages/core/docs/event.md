# core/event — таблицы долговременного журнала событий

## Что в папке

- `sql.ts` — единственный файл: две таблицы, `event_sequence` и `event`.
- Движка событий в папке нет вообще: ни подписки, ни публикации, ни шины.

## Ключевые файлы

- `packages/core/src/event/sql.ts` — `EventSequenceTable`, `EventTable`.

## Важные детали

- `event_sequence`: `aggregate_id` — primary key, `seq` — `integer().notNull()`, `owner_id` — `text()` без обязательности. Это счётчик последнего выданного номера события для агрегата; владелец агрегата (`owner_id`) хранится рядом с тем же счётчиком.
- `event`: `id` (тип `Event.ID` из `packages/schema/src/event.ts`), `aggregate_id` — `.notNull()` со ссылкой на `event_sequence.aggregate_id` и `onDelete: "cascade"`, `seq`, `type`, `data` — `text({ mode: "json" })` типа `Record<string, unknown>` с `.notNull()`.
- Порядок событий держится уникальным индексом `event_aggregate_seq_idx` на `(aggregate_id, seq)`. Повторная вставка с тем же номером невозможна — это и есть защита от двойной публикации.
- Второй индекс `event_aggregate_type_seq_idx` на `(aggregate_id, type, seq)` обслуживает чтение подмножества событий одного типа в хронологическом порядке.
- `created` — `integer().notNull().default(0)`, а не часть `Timestamps`: у события своё единственное поле времени со значением по умолчанию, а не пара created/updated.
- `data` аннотирован `$type<Record<string, unknown>>()`: тип полезной нагрузки не проверяется на уровне схемы таблицы, он приходит сверху при декодировании события.
- Удаление агрегата каскадно удаляет его события: журнал привязан к агрегату, а не хранится вечно сам по себе.

## Связи

- `packages/core/src/bus.ts` — реальный движок: по результату поиска по именам таблиц он использует и `EventTable`, и `EventSequenceTable` (выдача номеров). Это то место, где журнал пишется и читается.
- `packages/core/src/session/stats.ts` — читает `EventTable`: статистика сессий собирается из журнала событий.
- `packages/core/src/database/v1-migration.bun.ts` — упоминает `EventSequenceTable` при переносе состояния прошлых версий.
- `packages/schema/src/event.ts` — источник типов `Event.ID` и схем событий, которые декодируются при чтении.
- `packages/core/src/bus.ts` и `packages/core/src/session/stats.ts` — единственные потребители журнала; отдельного документа по механизму шины в `packages/core/docs` нет.

## Ловушки

- Папка называется `event`, но событий не реализует. Поиск подписчиков, `publish` или `subscribe` по этому каталогу ничего не найдёт — всё это в `bus.ts`.
- `data` хранится как JSON без проверки схемы. Форму журнала держит код чтения; испорченная полезная нагрузка всплывёт при декодировании, а не при записи.
- Номера событий выдаёт `event_sequence`, а уникальный индекс в `event` только запрещает дубликаты. Вставка события без предварительного взятия номера из счётчика упадёт по уникальному индексу.
- `owner_id` необязателен: события без владельца пишутся, и по одной таблице нельзя судить, чьи они.
- `created` по умолчанию равен `0`, а не «сейчас». Значение времени проставляет вызывающий код; если он этого не сделал, событие будет выглядеть как созданное в эпоху Unix.
